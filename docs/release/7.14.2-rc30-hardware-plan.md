## 0. What rc30 is, and what it is not

**There is no rc30 tag and there cannot be one.** `.github/workflows/release.yml:40-46` derives `TAG_VERSION="${GITHUB_REF_NAME#v}"` and hard-fails unless it equals the `project(... VERSION ...)` string in `CMakeLists.txt`, which is `7.14.2`. A tag `v7.14.2-rc30` yields `TAG_VERSION=7.14.2-rc30 != 7.14.2` and the `validate` job exits 1 before anything builds. Only `v7.14.2` FINAL can ever pass that gate.

**So the artifact under test comes from the branch CI run, not a release.** `.github/workflows/ci.yml:363-369` uploads:

```
firmware-v7.14.2-862e2610          <- artifact (name = firmware-v${fw_version}-${git_short})
  firmware.keepkey.v7.14.2-862e2610-firmware.keepkey.bin
  firmware.keepkey.v7.14.2-862e2610-*.elf
```

Two properties of that artifact the tester must internalise:

1. **It is unsigned.** `ci.yml` has no signing step; signing only happens in the release workflow, which cannot run (above). Expect the bootloader to show the unofficial-firmware warning and to **wipe storage on install**. Confirm this at flash time and write it down — if the device comes up *already initialised* after flashing, that contradicts the storage-wipe model and is itself a finding. Nothing in this plan can support any claim about signed-upgrade storage preservation.
2. **The version string in the CI *test-report PDF* is not trustworthy** — `ci.yml:731` runs the same `grep -oP` inside a BusyBox container where `-P` does not exist, with `|| echo "unknown"` (#467). The *artifact* name is produced on `ubuntu-latest` with GNU grep and is correct. Identify the build by the device's own `Features` banner and the `.bin` sha256, not by any PDF header.

**Known-red CI state: 22 integration failures, zero firmware defects among them.** Per `docs/release/7.14.2.md:340-353` (`22 failed, 362 passed, 47 skipped`, 134 s with the #477 per-test timeout):

| count | message | why it is red |
|---|---|---|
| 9 | `Transaction signing disabled by policy` (TON) | documented BREAKING gate; suite must opt in |
| 5 | `Chain Id out of bounds` | #445 working as designed; fixed by python-keepkey #215 |
| 3 | `Enable AdvancedMode to blind-sign` (TRON) | documented BREAKING gate |
| 2 | `Timeout >60.0s` | extra disclosure screens the pinned suite never acks (#466) |
| 1 | `Arbitrary contract data signing disabled by policy` | 0x `transformERC20` via #468 |
| 1 | `Enable AdvancedMode to blind-sign typed hashes` | documented BREAKING gate |
| 1 | `Structured EIP-712 disabled pending canonical display hardening` | deliberately disabled |

**Do not "fix" firmware for any of these.** Every one of the 22 is a stale pinned expectation. This plan produces hardware evidence for all seven rows — that mapping is in the final checklist — which is precisely what the release notes currently record as resting on diff-reading alone.

`deps/python-keepkey` is pinned at `81e581f`, a commit on an unmerged topic branch, and the release notes say the pin must be updated before tag. **Every script below runs against that pinned client.** The repin is expected to change 6 of the 22 test results; it must not change *device* behaviour. If it does, re-run the affected tests.

**Evidence standard.** A photograph proves what was drawn. It does not prove what was not drawn, it does not prove memory safety, and it cannot show a pre-fix screen on a post-fix build. Sections 3 and 4 say exactly where those limits bite.

### 1.4 The one shared cancel helper

The device has one button and **no reject**. `confirm_helper()` returns false only for a host-sent `Cancel`/`Initialize` tiny-message arriving while a `ButtonRequest` is outstanding (`lib/board/confirm_sm.c:249-256`, whitelisted in `lib/board/messages.c:357`). No stock client sends one — `BaseClient.call` just ButtonAcks and blocks. Tests 2, 3 and 5 all need this, so use one helper:

```python
def ack_photograph_then_cancel(t, msg, label, dwell=10):
    t.session_begin()
    try:
        t.write(msg)
        r = t.read_blocking()            # ButtonRequest
        t.write(proto.ButtonAck())       # screen is now up
        print('PHOTO %s: %ds -- DO NOT TOUCH THE BUTTON' % (label, dwell))
        time.sleep(dwell)
        t.write(proto.Cancel())          # tiny message, mid-screen
        return t.read_blocking()
    finally:
        t.session_end()
```

Back-to-back writes are safe: both `WebUsbTransport._write` and `HidTransport._write_usb` emit a single 64-byte report prefixed with report-ID 63, which is what `msg_read_tiny()` (`messages.c:322-332`) requires, and neither needs an intervening read. **A physical hold during this helper destroys the evidence.**

### 1.5 Photograph protocol

- Photograph the **request** screen — the one with the round hold indicator — *before* pressing. Frame the whole 256×64 OLED including the title row.
- Titles render **UPPERCASE** (`kk_strupr` at `lib/board/layout.c:242`, called from `layout_standard_notification` at :301). Bodies do not: EIP-55 mixed-case addresses and lowercase hex digests stay as written.
- Capture host stdout for every run: `... 2>&1 | tee T<n>.log`. Several pass criteria are half-photo, half-terminal.
- Name files `T<test>-<screen>.jpg` matching the screen IDs below.
- **The "no screen" rule.** Several tests pass by drawing *nothing*. A photo of the home screen is not evidence on its own. It counts only when paired with (a) a control frame in the same session that *does* draw, and (b) the host returning a `Failure` in tens of milliseconds. If a refusal screen were being drawn, `confirm_helper()` would block on the button and the host call would **hang**, not return. A hang is a fail.
- Budget: **~116 photographs** across 12 tests.

### T6 — Exact-byte pager for signed message payloads (#428, #410, #432)

**Changed.** `424294ccc`. Before, the three SignMessage handlers passed the protobuf `bytes` field straight into `confirm(…, "%s", …)`. ## 3. What CANNOT be verified on hardware

These are not scheduling gaps. Each is unreachable in principle from a physical rc30 device, and the release record should say so rather than let adjacent evidence read as coverage.

**3.1 — `1e30736ed`'s entire payload (EIP-712 cancel propagation).** The commit converts `confirmName()`/`confirmValue()`/`dsConfirm()` from `review()` to `confirm()` and propagates `USER_CANCELLED` through `parseVals()` so `encode()` aborts before a hash exists. Every one of those call sites sits behind `e712_types_values()`, which `424294ccc` made unreachable by hardcoding `ethereum_structured_eip712_enabled()` to `false` two statements earlier. T9 step 6 confirms this is a hard disable, not a policy gate. Two independent blockers: (a) reachability needs a firmware image built with that function returning `true` — a deliberately un-shipped variant, which tells you nothing about the release artifact; (b) a host that refuses needs a concurrent `Cancel` writer. **Currently covered only by `unittests/firmware/ethereum.cpp:78`, which checks error-code numbering, not the flow. Its correctness is a code-review claim, not a hardware one — do not let the endpoint disable read as evidence for it.**

**3.2 — `confirm_helper()`'s SOURCE-truncation branch.** The guard fires on `truncated || render_incomplete`, where `truncated` is set when `vsnprintf()` overflows `strbuf[BODY_CHAR_MAX=352]`. `Ping.message` caps at 256, so T5 tops out at 255 chars and can never reach it. The obvious long-host-string path (raw signed bytes) is pre-chunked by `confirm_bytes_format_page()` into pages that fit, so it never overflows either. Reaching it needs a message type whose formatted body can exceed 351 characters — none was found — or a DEBUG_LINK build plus a purpose-built confirm caller, i.e. a firmware change. **T5 proves the RENDER half only.**

**3.3 — The newline-wrap regressions** (`0b2f08185`, and `7e07b2d92`'s "a newline is only honoured if the row it asks for exists"). The attack shape needs a benign prefix plus ~255 newlines plus a hidden suffix inside a 352-byte buffer; `Ping` cannot carry it. Pinned by `unittests/board/board.cpp` only.

**3.4 — Both memory-safety fixes: #430's 19-byte Binance stack overflow and `base_to_precision`'s one-byte write past `dest[dest_len]`.** T12 steps E and B photograph the *corrected rendering*, which is necessary and not sufficient: a correct screen is equally consistent with the overflow being gone and with it landing on padding. Absence of a crash on one run is weak evidence. Settling these needs the board-unit gtests (`Board.BaseToPrecisionKeepsEveryDigit`, `Board.BaseToPrecisionRespectsCapacity`) on the host, or an ASAN/valgrind emulator build driven with the same messages. Neither is a hardware photo.

**3.5 — Whether a `BLOCKED` screen was dismissed by the user or cancelled by the host.** Both screen-showing gates call `(void)review(...)` and discard the return; the caller sends the same `Failure` either way. The outcome is identical **by construction** — no photo and no host output can separate them. A code-review note, not a testable property.

**3.6 — `confirm_bytes()`'s `if (take == 0) goto cleanup`.** The widest escape token is 26 px against a 225 px × 3-row body, so a single token always fits and `take` is never 0 for a non-empty payload. Dead defensive code, not a coverage gap.

**3.7 — #427 (EIP-1559 chain-id byte truncation).** Already on the base at `1af2ffe7de`, not in this range, and invisible on the OLED — it needs a signature-recovery check, not a photograph.

**3.8 — Any "before" screen.** No photo taken on rc30 can show pre-fix behaviour. Every "a FAILING photo looks like…" string in this plan is derived by reading the base tree, not observed. A true A/B needs a second device flashed with v7.14.1 running the identical scripts — and note that T12's A5, C and E diverge before reaching a screen there, so a strict A/B is only meaningful for T12's A1-A4, B and D.

**3.9 — Storage preservation across a signed upgrade.** The artifact is unsigned (§0). This run cannot support any claim in that area.

## 5. Where the cards disagree, and what is thin

Stated plainly rather than smoothed over.

1. **Transport (resolved, but only by one card).** Five cards assert `import config` "autodetects HID/WebUSB" and is fine. One card actually ran it on this machine and documented the `TypeError: expected bytes, NoneType found`. Reading `tests/config.py:70-80` confirms the failing branch exactly. **Trust the card that ran it** — §1.2's shim is mandatory, not optional, and 5 of the 8 pre-written scripts need the one-line patch.

2. **AdvancedMode persistence — genuinely unresolved, three-way.** T10 and T11's cards assert it is committed to flash and dutifully restore it. T8's card notes that `efa18ad77` and `b53b63b0a` both assert in their **commit messages** that it is session state and build their risk analysis on that. Prior rc29 hardware notes record it as "proven off after power cycle". The code (`storage.c:803/862/920/990`, bit 12) reads as persisted. **T8 leg C settles it. Until then, every test re-asserts the policy at its start rather than assuming — that is why the setup steps look redundant.** If it persists, two commit messages need correcting before release.

3. **T4 is the weakest card as written** — it demands a DEBUG_LINK build (not the release artifact), uses debuglink auto-button, and asserts that host-Cancel injection is impossible for a normal client, which three sibling cards disprove. §2/T4 prescribes the rewrite. Do not run it on a debug image and file the result as release evidence.

4. **T12 is the largest and its Solana leg the most fragile.** Nine steps, 27 screens, one hand-serialised Solana message. It also contains a deliberately expected FAIL (A4). Budget a separate sitting and read the A4 note before shooting it.

5. **T3's authenticator leg has no fixture precedent anywhere in the tree** and depends on undocumented `Ping`-prefix control bytes. Verify the prefixes first or leg A fails silently rather than loudly.

6. **T5's 118-char step predicts a NEW off-by-one in the commit under test.** Record it separately from the pass/fail verdict. It is the single highest-value observation available from this batch, and it is a prediction from reading `draw.c:215/226` — the photograph is what decides it.

7. **Three tests photograph the same #433 `BLOCKED` screen** (T8 A2, T10 RUN A, T11 leg B), and two photograph the same `EIP-712 BLIND SIGN` screen (T8 B4, T9 photo 4). T8 A2 and T9 are the primaries; the others are corroboration. Do not count them as independent evidence.

8. **T10's RUN C payload is synthetic** and its decode behaviour is a prediction from reading `zxtransERC20.c:100-108`, not an observed fact.
