# 7.14.2 — security release

Cut from `1af2ffe7de`: the head of `develop` on this fork and on
`keepkey/keepkey-firmware`. That commit is the shipped **v7.14.1** release plus 12
commits, all EVM bugfixes. Scope is security and bugfix only, on the full
firmware, ahead of the bitcoin-only split.

## Base selection, and a branch that was not it

`develop` contains v7.14.1 in full — `v7.14.1...develop` is *ahead 12, behind 0* —
so cutting from `develop` ships the active release plus the EIP-1559 fixes, and
nothing needs merging in first.

A branch named `release/7.14.2` previously existed at `199e42a0`. It was **not** a
successor to v7.14.1: it was last touched 2026-05-15, three weeks before v7.14.1
published on 2026-06-05, and it sat 33 commits behind `develop` — still carrying
the EIP-1559 chain-id truncation. Building from it would have regressed users. It
is preserved as `abandoned/7.14.2-20260515`.

Two related traps, recorded so the next person does not lose a day to them:

- Upstream `master` is **not** the release branch. It is at 7.14.0-era code and
  reports *diverged* against v7.14.1. Releases are tagged off `develop`.
- A local clone can have `develop`/`origin/develop` pointing at an orphaned 7.15.0
  commit (`4895b8155`) that is the head of no branch on GitHub. Resolve refs
  against the remote and read with an explicit SHA:
  `git show 1af2ffe7de:<path>`.

## Already on the base

Fixed at `1af2ffe7de`, shipping in this release, no work required:

- **EIP-1559 chain-id truncation** (#427, `ed6db167c`). `hash_rlp_field(&chain_id,
  sizeof(uint8_t))` hashed only the low byte on little-endian, so any chain id
  >= 256 produced a signature recovering to a sender the user does not control:
  Base 8453 hashed as 5, Arbitrum 42161 as 177, Avalanche 43114 as 106. Fund-loss
  class. The legacy EIP-155 path was unaffected.
- EIP-1559 fee display overcount and missing `max_priority_fee_per_gas` (#429).

## Threat model

The defects below are reachable by a **malicious or compromised host** talking to
an unlocked, PIN-authenticated device over USB. For a hardware wallet that is the
threat model that matters: the display exists precisely to protect the user from
an untrusted host. None requires the seed, and none requires physical access
except where stated.

No evidence of exploitation in the wild. No CVE has been assigned for any of
these; identifiers cannot be self-declared, and advisories will follow the fix.

reach no user today. Recovering them is the bulk of this release.

## Evidence standard

Memory-safety findings (#411, #416, plus the Binance and `base_to_precision`
defects held for a later cut) are claimed as **memory corruption and probable
crash** only. Any stronger claim — execution control or key disclosure — requires
a release-build PoC on device or emulator, and must not appear in release notes
without one.

The EVM calldata findings (#413, #414, #415) each need one complete transaction
PoC recording what the device displayed, the exact bytes signed, and the on-chain
effect.

## Out of scope

Zcash, dice entropy, BIP-85, clear-sign attestation, the bitcoin-only variant.
Release-pipeline integrity defects are tracked separately: they need no firmware
tag and must not gate this release. Medium and low severity firmware findings are
held pending a scope decision.

**#416, the 10-iteration PIN KDF, is deliberately out of scope.** It requires an
attacker to extract a flash image first, which is a different threat model from
the rest of this set — those are reachable by a malicious USB host against an
unlocked device with no physical access. It is also not a self-contained change:
raising the count needs a persisted KDF-version discriminator, which is a
storage-format change, which pulls in a downgrade policy. The 7.15 line built that
machinery and shipped it switched off for the same reason, so 7.15 is not ahead of
7.14.2 here — both wrap at 10 iterations today. The reasoning, including why a
trial-unwrap ladder would silently lock out any device that later runs older
firmware, is recorded on the issue.

**Two related defects are also deliberately not fixed here**, and the release notes
must not imply otherwise:

- The THORChain **router pin** (part of #415). The router address migrated
  v1 -> v3 -> v4; pinning this tree's literal would send every current mainnet
  THORChain swap to the blind-sign path, which is a worse outcome than the bug.
  Closing it needs a live router address verified off-tree, so it is filed
  separately.
- TRON destination **verification**. #405 stops the device displaying a
  destination it cannot verify; it does not verify one. That needs a `raw_data`
  parser, which is 7.15 work.

## Status

**Strong release candidate. Not a defensible security release.**

Post-review signing hardening for this release is documented in
[`docs/security/7.14.2-signing-hardening.md`](../security/7.14.2-signing-hardening.md).
It closes the identified signed-content disclosure and AdvancedMode policy
cluster with focused patches and disables structured EIP-712 pending a canonical
implementation. It does not change the no-tag conclusion or the release gates
below.

The supportable statement today, and the only one to use publicly:

> This branch fixes 16 verified defects with ARM regression coverage. Release
> remains blocked on two High-severity findings, complete residual-finding triage,
> and hardware verification.

Do **not** claim "all critical/CVE-level issues addressed". Two rounds of
adversarial review have each found High-severity defects in work that had been
called ready, three of them introduced by this branch. The rate is not visibly
decaying, so the prior is that a third round finds more.

**Change freeze.** Unrelated changes are frozen on this branch from now, so the
target stops moving. Only work that closes a gate below lands here.

## BREAKING: what a default-configuration device can no longer do

This must lead the release notes. The picture changed once the exact-byte pager
landed, so the table below is the current state, not what #440 originally set.

| Path | Default device | Why |
|---|---|---|
| ETH `personal_sign` | **works** | `confirm_bytes()` paginates every signed byte, so #432's gate was dropped |
| TRON `SignMessage` | **works** | same — pager, gate dropped |
| Bitcoin-family `SignMessage` | **works** | same |
| ETH **structured EIP-712** | **DISABLED** | withdrawn pending complete canonical hardening |
| ETH precomputed typed hash | AdvancedMode | the device cannot bind the hash to any typed data it displayed |
| ETH arbitrary contract data | AdvancedMode | no pager exists for streamed calldata; see #400 and #428 |
| TRON `SignTx` | AdvancedMode | `raw_data` still cannot be parsed on this line (#405) |
| EVM `SignTx` with **no `chain_id`** | **REFUSED** | produced a pre-EIP-155 signature replayable on every EVM chain, and the confirm screen named no network (#445) |
| 0x `transformERC20` over 1024 bytes | **REFUSED** by default, AdvancedMode to sign | was clear-signed with an undisclosed `transformations[]` tail; now falls through to the raw-hex path (#444) |

**On the 0x change — this affects real swaps, not an edge case.**
`EthereumSignTx.data_initial_chunk` holds 1024 bytes and 0x aggregates across liquidity
sources, so production routes exceed it. Measured, not estimated: the recorded mainnet
transaction in `deps/python-keepkey/tests/test_msg_ethereum_erc20_0x_signtx.py`
(etherscan `0xcf94f79d…`) is **1480 bytes** of calldata — its second transformation
(`PayTakerTransformer`) starts at byte 1060, already past the boundary. Dropping that
transformation would leave the funds in the Exchange Proxy, so no host emits a shorter
form.

Those swaps previously showed a clear-signed "Transform ERC20" screen while the tail
streamed in unshown. They now reach the generic contract-data path, and **on a
default-configuration device that path is a refusal**: `AdvancedMode` is off by default
(`include/keepkey/firmware/policy.h:34`) and `lib/firmware/ethereum.c:808` answers with
`fsm_sendFailure(ActionCancelled, "Arbitrary contract data signing disabled by
policy")`. Enabling AdvancedMode signs it and shows the raw-hex disclosure. That is the
policy — never block someone from their own funds, but never present bytes the device
did not interpret as though it had — but the release notes must say plainly that the
default answer for a 0x swap is now "no, turn on AdvancedMode", not "yes, with a worse
screen".

**This closes #444, which was scoped to the streamed tail.** It does not close the
adjacent in-buffer weakness, and that is deliberate: the gate proves the calldata was
*received*, not *displayed*. `transformERC20`'s ABI head is 164 bytes and the decoder
shows four values, all inside it, so a payload that fits one chunk still clear-signs
with up to 860 bytes of `transformations[]` never shown. That primitive is unchanged by
this commit — the code it lives in is untouched — and it is tracked by **#473**.

Not #414, which an earlier revision of this document named. #414 is the unread ABI
**offset word** — a caller placing its real arguments elsewhere so the hardcoded
positions display plausible-but-wrong values. That is misdirection and it is fixed at
head. #473 is non-disclosure: bytes never read or shown at all. Different failure mode,
and it needed its own issue rather than inheriting one that was about to close.

**The bounded-outcome argument does not hold on every allowlisted chain.** The four
displayed values are static head words and are read correctly. The argument for the old
exemption was that the input amount and minimum output amount bound the loss. Two things
undercut it. First, that bound is enforced by the 0x Exchange Proxy, which is
upgradeable, so it is not a guarantee this firmware can make. Second and more concretely:
`TokenType.chain_id` and `tokenByChainAddress()` are `uint8_t`
(`include/keepkey/firmware/ethereum_tokens.h:42,54`), so of the six chains in
`zx_isExchangeProxyChain()` three truncate — Base `8453 -> 5`, Arbitrum `42161 -> 177`,
Avalanche `43114 -> 106`. The lookup misses, returns `UnknownToken`, and
`ethereumFormatAmount()` short-circuits to the literal `"Unknown token value"`
(`lib/firmware/ethereum.c:347`) for **both** operands. On those chains the screen reads
"Input Unknown token value / Output Unknown token value" and displays no bound at all.
Tracked as **#455**; the immediate remedy is to drop those three chains from the
allowlist so they take the raw-hex path.

**AdvancedMode is session state, not a setting** — it resets on power cycle, proven
on hardware during the 7.15 work. Anything gated by it must be re-enabled on every
replug, which is a materially worse user experience than a persisted policy.

### What this means for hosts

Vault and the browser extension need a matching change or the device will appear
broken to existing integrations:

- **Structured EIP-712 signing will fail outright.** Any dApp flow that sends
  `Ethereum712TypesValues` needs a fallback or a clear error.
- **Token approvals and swaps** are contract data, so they are AdvancedMode-gated.
- Sign-In-With-Ethereum is fine again — that was the largest compatibility risk in
  #440 and the pager removed it.

### The principle worth keeping

Where the device can show the user every byte it is about to sign, it should show
them and let them decide. A policy gate is what you reach for when you cannot show
them — not a substitute for disclosure you could have built. Two of #440's three
gates were removed by building the disclosure instead; the three that remain are
the cases where the device genuinely cannot describe what it would be signing.

## Release gates

Every one of these must close before a tag. They are ordered.

1. **#429 first — setup must behave as a transaction.**
   No security setting is committed until the final on-device confirmation;
   out-of-sequence messages are rejected; cancellation rolls back pending state.
   Test permutations of Reset / Recovery / Cancel / EntropyAck, not just the one
   known sequence.

2. **#428 — redesign around a stronger invariant**, not a patch to the measurement.
   The invariant: *the user approves exactly the semantic content being signed.*
   Never measure an already-truncated buffer. Handle whitespace and control
   characters explicitly. Paginate or reject oversized fields. Add property and
   fuzz tests over spaces, newlines, truncation boundaries, UTF-8 and embedded
   control characters.

3. **Independent re-exploitation of both fixes** — reviewers must attempt to break
   them, not inspect the patches.

4. **Hardware verification round**, with OLED evidence for every
   confirmation-path change.

5. **Triage all 55 remaining audit findings.** They need not all block, but every
   Critical/High candidate is resolved or explicitly accepted with documented
   reasoning.

6. **A final adversarial round over the complete candidate.** Zero newly
   discovered High/Critical issues before tagging.

Note on #429: that it predates this release does not reduce its blocking
significance. Once known, shipping a security-focused release containing a
reproducible path that silently removes setup protections is not defensible.

### What the hardware round actually established

Two findings, and an honest accounting of the rest.

**AdvancedMode persists across a power cycle.** Measured at T8 leg C: still
enabled after a physical replug, which the code supports (`storage_commit`,
bit 12). **Both `efa18ad77` and `b53b63b0a` state in their commit messages that
"AdvancedMode is session state (it is off again after a power cycle)" and build
their risk analysis on it.** That is wrong on this build: once a user enables
blind-signing it stays enabled until explicitly revoked. The blast radius is
"until revoked", not "until unplugged". **Release-note correction.**

**#485** — the Cut Off screen promised to show the hidden text and redrew the
same clipped body. Fixed by #488. Found by reading `confirm_sm.c:441`, not by
the device.

**Most of the wire-level checks duplicated the emulator suite**, which asserts
the same `Failure` codes and signatures in CI. That is worth stating plainly so
the next round is aimed better: the screens and the press durations are what
hardware alone can establish, and they are now respectively automated (#487) and
measured (T13).

**One finding was retracted.** #484 and its fix PR #486 rested on "the device
confirmed with no press"; the tester was pressing. The refuting control — a
single untouched confirm screen — took one minute and belonged before the issue
was filed. A near-repeat during T13 was caught only by asking the tester what
they had done rather than inferring it from a timing.

### CI was measuring the wrong release

`FW_VERSION` detection used `grep -oP`, which BusyBox lacks, so it always fell
back to **7.14.0** on the 7.14.2 branch (#467, fixed in #487). Since SECTIONS
entries are selected by `ver_ge(fw_version, min_fw)`, **every test gated to
7.14.1 or later was excluded from the screenshot filter and from report
validation** for the whole release. That is why the suites this release changed
captured no screens.

Third instance of one pattern in this release: a check that ran, went green, and
measured something other than its name — after the Stage-1 skip (`ci-gate`,
#474) and the integration deadlock (#477). The per-test screenshot audit in #487
closes this variant.

### RELEASE INVARIANT: disclosure never yields to a stale test

**Tests adapt to newly required disclosure. Firmware disclosure is never removed to
satisfy a stale test.** The dependency runs in one direction only.

This is written down because the pressure to invert it is real and arrives disguised
as housekeeping. The integration suite is red, the quickest way to green is to stop
showing a screen, and the commit that does it looks like a test fix. The extra
THORChain screens disclose affiliate-fee bytes that were **previously signed
invisibly**; deleting them to make CI pass would reintroduce the defect this release
exists to close, and it would look like progress while doing it.

If a test fails because the device now shows more, the test is wrong.

- Do not assess the integration suite sequentially against one emulator. A killed hang
